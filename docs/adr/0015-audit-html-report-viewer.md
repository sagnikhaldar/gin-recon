# ADR 0015: A Second Self-Contained HTML Viewer for the Audit/Inventory Report

## Status

Accepted. Implemented as `internal/format/audit_html.go`'s `AuditHTML(rep *report.Report, cfg *config.Config) ([]byte, error)`, a sibling to `internal/format/html.go`'s `HTML` sharing no template or JS with it: a metrics strip, a `findingsSection()` present only when the embedded JSON carries a `findings` key (i.e. `rep.Command == report.CommandAudit`, since `Report.MarshalJSON` omits it entirely otherwise), a searchable/auth-filterable `routesSection()` table (`#route-filter` input, `#auth-filter` dropdown, both wired the same client-side-only way as `html.go`'s `filterInput`), and a `diagnosticsSection()` over `Report.Diagnostics`. Wired into `cmd/gin-recon/main.go`'s `writeReport` as `audit.html`, the fixed companion file for `--format json` with `--out`, exactly mirroring `api.html`'s existing companion relationship to `--format openapi` (see `auditHTMLCompanionFilename` and the `f == cli.FormatJSON` branch alongside the existing `f == cli.FormatOpenAPI` one). `docs/cli-contract.md` documents the pairing next to `api.html`'s. Tests: `internal/format/audit_html_test.go` (self-contained-page, findings-conditional-rendering, routes/diagnostics content, filter wiring, script-tag-escaping regressions) and `cmd/gin-recon/main_test.go`'s `TestRunJSONFormatAlsoWritesAuditHTMLCompanion`. Verified end to end against a real internal repository's audit report (758 routes, 94 findings) producing a well-formed, fully self-contained `audit.html` with the real route/finding data round-tripping through the embedded JSON.

Follow-up fix: a review comparing this page against `routes.md`'s own header (which already prints "Scan: N package(s), N file(s) analyzed — complete" and the build profile/GOOS/GOARCH) found the initial version's header/metrics omitted that same `ScanCoverage`/`BuildContext` detail — showing only a bare `complete: yes/no` boolean. `render()`'s header line and `metricsSection()` now also surface `cov.profile`, `cov.buildContext.{goos,goarch}`, `analyzedPackages`/`discoveredPackages`, `analyzedFiles`/`discoveredFiles`, and (only when nonzero, to avoid clutter in the common all-succeeded case) `failedPackages`/`failedFiles` — bringing `audit.html` to parity with what `routes.md`/`routes.txt` already showed. Covered by `TestAuditHTMLSurfacesBuildContextAndScanCoverageDetail`.

## Context

`api.html` (ADR 0009) renders exactly one document: the generated OpenAPI spec (`openapi.json`) — paths, operations, request/response schemas, descriptions. It has never rendered `routes.json`/`routes.md` — the actual audit/inventory report, carrying per-route auth classification, full middleware chains, source locations, scan coverage, diagnostics, and (for `audit`) `Summary`/`Findings`/`PolicyEvaluation`/`ActiveExceptions` (`internal/report/report.go`'s `Report` struct). A reviewer who wants an interactive, searchable view of *the audit itself* — not the API surface it happens to expose — has exactly two options today: read raw `routes.json`, or scroll a static Markdown table with no search, no filter, and no summary metrics.

A reference HTML render from a sibling tool (`express-recon`'s `render` command, inspected directly at `/home/sagnik/Tools/express-openapi-inventory/audits/pb-be-files/html/index.html` this session) makes the gap concrete: it renders that tool's equivalent of `routes.json` as a page with a metrics strip (route/finding/coverage counts at a glance), a Findings section (severity-tagged, human-readable), a searchable + status-filterable routes table (method, path, auth, source, full middleware chain), and a Diagnostics section — none of which gin-recon has ever produced in HTML form for its own audit data.

## Decision

Add a second, independent self-contained HTML report, `audit.html`, rendering `routes.json`'s actual content — not a variant of `api.html`, not a shared template. The two viewers stay scoped to what they already do well: `api.html` is the API-consumer's view (what does this service expose), `audit.html` is the reviewer's view (what does this service's route surface actually look like, security-wise). Concretely:

- **Content**: a metrics strip (total routes; proven/public/unknown counts; scan coverage completeness; findings count when present); a Findings section rendering `Summary`/`Findings` when the source report is from `audit` (absent entirely for an `inventory` report — these fields are already schema-optional exactly along that line, per `report.go`'s own comment on why `Findings`/`Summary` are tagged `json:"-"` and hand-marshaled); a searchable, status-filterable table of every route (method, path, auth status, middleware chain, handler, source) — client-side filtering only, no server, matching `api.html`'s existing filter-input precedent (`internal/format/html.go`'s `filterInput` in `render()`); a Diagnostics section rendering `Report.Diagnostics` in plain readable form (this is where `swag-router-mismatch`, `openapi-spec-orphan-operation`, `gin-library-entry-point`, etc. all become visible without reading JSON).
- **Single self-contained file, matching gin-recon's existing convention exactly** — not the reference's separate `assets/report.css`/`report.js`. `api.html` already proved this works and stays offline/dependency-free (ADR 0009); there is no new reason to diverge from it for a second viewer, and a second convention would only cost future maintainers a second mental model for no benefit.
- **Trigger**: requesting `json` with `--out` also always writes `audit.html` alongside `routes.json`, with no separate opt-in — the same "requesting `openapi` with `--out` also always writes `api.html`" rule `docs/cli-contract.md` already states for the existing viewer, extended by the same reasoning to the format `audit.html` is actually derived from (`routes.json`'s data, not `routes.md`'s rendering of it). Both viewers can be requested in the same run (`--format json,openapi --out <dir>` yields all four files) since they read disjoint source documents and impose no ordering dependency on each other.
- **No new report field, no new diagnostic, no new precedence decision** — this ADR is purely a rendering decision over data every prior ADR already computed and already ships in `routes.json`. It changes nothing about what gin-recon analyzes, classifies, or trusts.

## Consequences

A reviewer gets the interactive, searchable audit view express-recon's reference already demonstrates is useful, without gin-recon taking on a second HTML-generation convention, a runtime CSS/JS bundler, or a dependency on the target report's `--format` selection order. The cost is one more generated file whenever `json` is requested with `--out` — a purely additive, backward-compatible CLI behavior change (existing scripts that only look for `routes.json` in that directory are unaffected; a new file appearing alongside it cannot break an existing consumer that doesn't already error on unexpected files, which would be an unusual and already-fragile assumption for any directory-scanning consumer).

## Rejected Alternatives

- **Extend `api.html` to also show audit data.** Rejected: it would conflate two different readers' needs (API consumer vs. security reviewer) into one page and one JS module, and `api.html`'s entire structure is built around iterating `spec.paths` — audit data (coverage, findings, full middleware chains) has no natural home in an OpenAPI-shaped page without either fabricating OpenAPI extensions for data that isn't OpenAPI-shaped, or forking the rendering logic internally anyway, at which point it's a second file in substance while pretending to be one in name.
- **Match the reference's separate CSS/JS asset files.** Rejected — no reason to introduce a second self-contained-file convention when the first one (`api.html`) already works and is already documented (ADR 0009); consistency has real value here and the reference's choice reflects a different tool's own conventions, not a technical requirement gin-recon needs to inherit.
- **Trigger `audit.html` off `md` instead of `json`.** Rejected in favor of pairing it with the format that is the actual canonical source of the data it renders (`routes.json`), mirroring `api.html`'s pairing with `openapi` (its canonical source) rather than with a human-readable derived rendering.
