# ADR 0014: Auto-Detect Existing OpenAPI Documents at Conventional Paths

## Status

Accepted. Implemented in `internal/analyzer/existingspec.go`: the fixed, ordered candidate list is `ExistingDocumentCandidates`; the three-way precedence (explicit > auto-detected > off) and the auto-detection probe loop are `ResolveAndReconcileExistingDocument`, which delegates to the unchanged `ReconcileExistingDocument` (ADR 0013) when `analysis.existingOpenAPIDocument` is set, and otherwise probes each candidate in order via the shared `loadExistingDocument`/`existingDocumentModel.hasAnyPathItem` helpers factored out of the original single-path loader so a winning auto-detected candidate is parsed exactly once, not re-parsed by a second call into `ReconcileExistingDocument`. The matching/merge body itself is `reconcileWithModel`, shared unchanged by both entry points. New config field `config.AnalysisConfig.DisableExistingOpenAPIAutoDetect` (`internal/config/config.go`, `analysis.disableExistingOpenAPIAutoDetect`, bool, default `false`) is wired in `cmd/gin-recon/main.go`'s `applyExistingDocumentReconciliation` alongside the existing `existingOpenAPIDocumentFrom`, via a new `disableExistingOpenAPIAutoDetectFrom` accessor following the same config-only pattern. See `docs/configuration-contract.md`, `docs/openapi-strategy.md#existing-openapi-document-reconciliation`, and `docs/report-contract.md` for the shipped contract.

## Context

ADR 0013 required `analysis.existingOpenAPIDocument` to be set explicitly before any reconciliation happened, reasoning by direct analogy to ADR 0010's `followModules`: "silently globbing a target repo for anything that looks like an OpenAPI file... is exactly the kind of implicit, un-reviewable magic ADR 0002/0003 already reject." Running this in practice against three real repos in the `Gin based repo` fleet (`docs/adr/0013`'s own implementation, validated in the same session) confirmed the mechanism works — but also confirmed the ergonomic cost the "config-required" stance imposes: getting reconciliation for those three repos required hand-writing three separate per-repo config files, one per document location, none of which a reviewer should reasonably be expected to do for the common case across dozens of repos.

That cost needs to be weighed against what ADR 0013's "opt-in" stance was actually protecting against, and the honest answer is: **less than `followModules` protects against.** `followModules` decides whether gin-recon trusts and analyzes an entire dependency module's *code* — a genuine expansion of what gets executed-in-analysis and what could feed into security classification. Existing-document reconciliation, as ADR 0013 actually built it, cannot do either of those things: `authStatus`/`security` are permanently walled off from this evidence source (ADR 0007's clause, restated in ADR 0013), a lower-precedence document field never overwrites a higher-precedence one, and a structural disagreement produces a diagnostic rather than a silent trust decision. The worst case of reconciling against the *wrong* file is a wrong description string a reviewer can see and ignore — not a misclassified auth boundary. ADR 0013's "opt-in" requirement copied ADR 0010's caution without re-deriving whether the same caution level was warranted for a mechanism with a structurally different (and much smaller) blast radius.

The session's own fleet testing surfaced the concrete failure mode a *naive* broad auto-discovery would hit, though: an unrelated, accidentally-created `swagger-api-docs/openapi.json` (a stray copy of gin-recon's own earlier output, left in ~25 repos by an unrelated background process) sits in the same repos as the genuine documents. A recursive glob for "anything that looks like an OpenAPI file" would happily pick that up and "reconcile" gin-recon's output against itself — a real, demonstrated risk, not a hypothetical one. This ADR's design has to survive that exact case, not just the three repos that went well.

## Decision

**Auto-detection is enabled by default, but only against a fixed, small, explicitly-documented list of conventional filenames — never a recursive or broad glob.** This is deliberately a much narrower mechanism than the "implicit file discovery" ADR 0013 rejected: that rejection was about *unbounded* guessing; a fixed allowlist checked in a documented, fixed priority order is closer in spirit to how `go.mod`, `Makefile`, or `.eslintrc` are conventionally auto-discovered by their respective tools without configuration — bounded, deterministic, and auditable by reading one list, not a search algorithm.

**The candidate list** (checked in this order, relative to `--src`, first one that exists *and* parses into a document with at least one path wins):

```
openapi.yaml, openapi.yml, openapi.json,
swagger.yaml, swagger.yml, swagger.json,
docs/openapi.yaml, docs/openapi.yml, docs/openapi.json,
docs/swagger.yaml, docs/swagger.yml, docs/swagger.json,
openapi/openapi.yaml, openapi/openapi.yml,
api/openapi.yaml, api/openapi.json
```

Deliberately excluded, on purpose, not by oversight: anything under `.gin-recon/` (gin-recon's own output — checking these would occasionally let a report reconcile against a stale copy of itself from a prior run); any filename containing `.base.` (swaggo's own convention for a partial *template* file meant to be merged by `swag init`, never a complete document on its own — confirmed empty of `paths` in every real instance found in the fleet); and, critically, `swagger-api-docs/` is simply never on the list — the fixed-allowlist design means an accidental directory with a plausible-sounding name is invisible to auto-detection by construction, not by a special-cased exclusion rule that could be forgotten elsewhere.

**Explicit configuration still wins outright.** `analysis.existingOpenAPIDocument`, if set, is used exactly as ADR 0013 defined — auto-detection never runs when it's set, since an explicit value is by definition more deliberate than a convention match. A reviewer with a document at a nonstandard path still configures it explicitly; nothing about that path changes.

**An explicit off-switch exists for a reviewer who wants zero surprises.** New field `analysis.disableExistingOpenAPIAutoDetect` (bool, default `false`). Setting it `true` restores ADR 0013's original behavior exactly — reconciliation happens only when `existingOpenAPIDocument` is explicitly set. This exists because "auto-detect by default" is a real behavior change for every future scan of every repo, including ones a reviewer has not yet audited for what sits at these conventional paths, and a global kill switch is cheaper than asking every team to discover the new default the hard way.

**Everything downstream of "which file was selected" is completely unchanged.** ADR 0013's parsing (fail-soft on not-found/invalid), matching (exact method+normalized-path, no fuzzy matching), merge precedence (analyzer-typed > swag > existing-document > placeholder), structural-compatibility gating, and orphaned-operation handling are untouched by this ADR. This ADR only changes how the *path* is obtained — auto-detected-by-convention now sits above "unset, feature off" and below "explicitly configured" in a three-way precedence, where ADR 0013 only ever had two.

## Consequences

Running gin-recon offline against a repo that already has a spec at one of the conventional paths — which, per this session's own fleet audit, is `use-be-api`, `sc-exp-platform-be`, and `sc-platform-tracking` today, and plausibly more repos in the future as teams adopt the convention — now gets genuine reconciliation with zero manual configuration, closing the exact gap this decision was raised to close. A repo whose document sits at a nonstandard path still needs one line of explicit config, unchanged from ADR 0013. A repo with no document at any conventional path, and none configured, behaves identically to today.

The cost is that "no `analysis.existingOpenAPIDocument` configured" no longer unconditionally means "no reconciliation happened" — a reviewer diffing two reports across a config change needs to know a file at a conventional path could now be a silent (in the sense of "not configured," not in the sense of "untraceable" — it still shows up as `route.existingDocument` evidence and real diagnostics) contributor. This is why the report continues to name its evidence sources explicitly per route rather than only at the top level: a reviewer inspecting any one route already sees exactly which evidence contributed to it, auto-detected or not.

## Rejected Alternatives

- **Recursive/broad glob for anything OpenAPI-shaped.** Rejected for the reason ADR 0013 already gave, now with a concrete demonstrated failure case (`swagger-api-docs/`) rather than a hypothetical one.
- **Auto-detect but require an opt-in flag to enable it (`analysis.autoDetectExistingOpenAPIDocument: true`, default false).** Rejected as not actually solving the problem raised: it reproduces ADR 0013's exact ergonomic cost one level up — a reviewer still has to know the feature exists and type a config line before getting any benefit. The whole point of "convention over configuration" is that the convention works without a reviewer having opted into knowing about it first.
- **Make auto-detection match ADR 0010's `followModules` precedent exactly (opt-in only, no default-on behavior).** Rejected per the Context section's core argument: the two features have structurally different blast radii, and applying `followModules`' caution level here was importing a precedent without re-deriving whether it fit.
- **Fuzzy-match additional filenames (e.g. anything ending in `-openapi.yaml` or containing "swagger" anywhere in the name).** Rejected: reintroduces exactly the unbounded-guessing risk a fixed list exists to avoid, for marginal convenience over just adding a specific new filename to the documented list when a real, common convention is found.
