# ADR 0009: Self-Contained HTML Viewer, Not Redoc, as the Default `api.html`

## Status

Accepted.

## Context

`audit --format openapi` (and `inventory --format openapi`) always writes `api.html` alongside `openapi.json` — a human-browsable view of the exact same OpenAPI 3.1 document, generated with zero AI and zero extra flags (see [openapi-strategy.md](../openapi-strategy.md)). express-recon's equivalent workflow instead points a user at a generic viewer — typically Redoc or Swagger UI — loaded from a CDN. Redoc in particular is a strong, polished, industry-standard renderer: persistent sidebar navigation, full-text search, and virtually no code for gin-recon itself to write or maintain. It is a reasonable default question to ask why gin-recon does not simply do the same thing.

Two properties of this project make that comparison closer than it first looks, but not equal:

- [ADR 0001](0001-static-first-v1.md) and [the threat model](../threat-model.md) commit gin-recon to offline-by-default operation as a load-bearing security property of the *analyzer*, not an incidental implementation detail — `GOPROXY=off`, no telemetry, no network egress during a scan unless a user explicitly opts in with `--allow-downloads`.
- `api.html` is gin-recon's own **output artifact**, not a third-party rendering step a user separately chooses to run. A report from this tool can describe unreleased, internal, or otherwise sensitive API surface (route paths, handler names, auth requirements). Whether the *viewer* for that report reaches out to the network is therefore not a separate concern from whether the *analyzer* does — it is the same trust boundary, just crossed one step later, at the moment a human opens the file rather than the moment gin-recon ran.

A CDN-loaded Redoc bundle would cross that boundary on every single viewing, from every machine that ever opens the file, not once at scan time: the CDN operator would learn, from request timing and referrer-adjacent metadata alone, that some organization is viewing an API surface document, independent of anything gin-recon itself ever transmits. Pinning the bundle by version and Subresource Integrity hash (as [the `openapi-doc` skill](../../skills/openapi-doc/SKILL.md) documents for its own manual, human-invoked Redoc option) closes the *tampering* risk but not the *network-egress-on-view* one, and it adds a second release cadence — Redoc's own — that gin-recon's own release process would need to track and re-pin.

## Decision

`api.html` remains a self-contained, dependency-free HTML page generated entirely from data gin-recon already computed for `openapi.json`: no external stylesheet, script, font, or CDN reference of any kind, and no network access required to open it, ever, on any machine. This is a hand-written, deliberately small vanilla-JS renderer (`internal/format/html.go`), not a Redoc/Swagger UI embed — see `escapeScriptClose` in that file for the adjacent, equally load-bearing requirement that a hostile scanned repository's own route/symbol text can never break out of the page's embedded `<script>` element.

Redoc (or Swagger UI, or any other CDN-hosted viewer) remains available, but only as an explicit, human-invoked *choice* made with full knowledge of the trade-off, documented in the `openapi-doc` skill as an alternative regeneration step for the specific case where a very large API's sidebar/search genuinely earns its keep over gin-recon's own flat, tag-grouped page — never as a built-in `--format` value or CLI flag. The distinction matters: a flag makes the offline/online trade-off one keystroke away from becoming the path of least resistance in a security tool whose whole premise is that "the safe path is the only path unless you go out of your way," where a documented manual skill step keeps that decision deliberate every time.

## Consequences

`api.html` opens correctly on an air-gapped machine, from a downloaded CI artifact, or on a machine actively scanning a hostile repository, with the exact same zero-network guarantee the rest of the tool provides. In exchange, gin-recon carries a small amount of its own view-layer code (`internal/format/html.go`, `internal/format/html_test.go`) rather than depending on an upstream project for it, and that page's UX (search, larger-API navigation) is capped at what this project chooses to build into it, not what Redoc already ships. If a future need (e.g. full-text search across thousands of operations) genuinely cannot be met by improving the self-contained page, the decision to revisit belongs in a new ADR, not a quiet CLI flag — the offline default for gin-recon's own generated output has the same status as the offline default for its analysis, and should be no easier to opt out of.

## Rejected Alternatives

- **Always embed/reference Redoc or Swagger UI from a CDN as the default `api.html`.** Rejected: contradicts ADR 0001's offline-by-default posture for gin-recon's own output artifact, not just its analysis step, and introduces a network round-trip (and a third-party's visibility into the fact that this report exists) on every single viewing rather than once at scan time.
- **Vendor a pinned Redoc/Swagger UI bundle into the binary and embed it locally (no CDN, but still Redoc's code).** Rejected for v1: still couples gin-recon's release cadence to an upstream JS project's, adds real binary size and a JS supply-chain surface this tool would then need to track (`govulncheck`-style scanning, license review) for a dependency that isn't even Go, for a UX improvement (search, sidebar) the self-contained page can approximate incrementally without it. Not permanently foreclosed — if a vendored-and-pinned approach is ever adopted, it should replace this ADR's decision explicitly, not bypass it silently.
- **Let `--format openapi` accept a `--html-renderer redoc` flag that fetches Redoc at generation time (network access already implied by the flag).** Rejected: this is the CDN option again with an extra step, and worse, it would mean gin-recon's own CLI — not just a human's decision — chooses to make a network request as part of "generating a report," which is exactly the boundary [the CLI contract](../cli-contract.md) and [threat model](../threat-model.md) draw around `--allow-downloads`-gated behavior today. Keeping this a documented manual skill step, not a flag, keeps that boundary intact.
