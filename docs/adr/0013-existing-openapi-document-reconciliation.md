# ADR 0013: Existing OpenAPI Document Reconciliation

## Status

Accepted. Implemented in `internal/analyzer/existingspec.go` (parsing, matching, merge/precedence, orphan collection), `internal/format/openapi.go`'s `applyExistingDocEvidence` (precedence-ordered application against swag/ADR 0012), `config.AnalysisConfig.ExistingOpenAPIDocument`, `model.Route.ExistingDocument`, and `report.ExistingDocumentReconciliation`. See `docs/openapi-strategy.md#existing-openapi-document-reconciliation`, `docs/report-contract.md#existing-openapi-document-reconciliation`, and `docs/configuration-contract.md` for the shipped contract.

Implementation note (format support): `internal/analyzer/existingspec.go`'s `loadExistingDocument` originally only called `libopenapi.Document.BuildV3Model()`, so a genuinely Swagger 2.0 document (top-level `swagger: "2.0"`, not `openapi: 3.x`) always fell into the "invalid" outcome below even though it parses as a real, valid document under an older format. Real-fleet scanning found this is not a hypothetical: several repos carry a hand- or swag-generated Swagger 2.0 document rather than OpenAPI 3.x. `loadExistingDocument` now tries `BuildV3Model()` first (unchanged behavior and precedence for the OpenAPI 3.x case) and falls back to `BuildV2Model()` only when that fails, normalizing whichever model built successfully into the same format-agnostic `docOperation` shape before matching. Every matching/merge/precedence/diagnostic rule described below — including the structural-compatibility check on path parameter names and the `openapi-spec-conflict`/`openapi-spec-orphan-operation` diagnostics — is unchanged and applies identically to a v2 or v3 source document; only which document a "valid" outcome accepts changed. This is a parsing-layer extension of the already-accepted decision below, not a new ADR.

One implementation note where this ADR's text left a choice open rather than an outright divergence: this ADR describes the merge rule in terms of "a resolved request/response type" as well as path parameters, but gin-recon's OpenAPI formatter does not yet infer request/response body schemas at all (v1 scope, `internal/format/openapi.go`'s own package doc comment) — there is no such resolved type for any document content to agree or conflict with yet. The structural-compatibility check implemented here therefore applies to the one schema-shaped field gin-recon does resolve today, path parameters (name and position, from Gin's own `:name`/`*name` syntax), plus a path parameter's own `description`, the one per-parameter content this document evidence can safely add. Prose fields (`summary`/`description`/`tags`/`deprecated`) are applied whenever present, ungated by the structural check, matching how ADR 0012 already treats swag's equivalent fields. When request/response schema inference is eventually built, this same document evidence source and its existing precedence position (below analyzer-typed evidence and swag, above the generic placeholder) extend naturally to those fields without needing a new ADR.

## Context

ADR 0007 already states the governing policy for this exact situation: "Existing documentation may enrich prose and provide schemas when code evidence is unresolved. A reviewed schema may refine code-derived evidence only when it is structurally compatible with all resolved fields and types. Conflicts retain the code-derived value, produce structured diagnostics, and mark the affected detail unrefined." That sentence was written before any mechanism existed to act on it — no code in this repository locates or parses a pre-existing OpenAPI/Swagger document from a scanned target repo. `github.com/pb33f/libopenapi` is already a dependency (`go.mod`), but today it is only exercised by `internal/format/openapi_roundtrip_test.go` and `sarif_roundtrip_test.go` to validate gin-recon's *own* generated output — never to read a document gin-recon did not produce.

ADR 0011 deferred this exact gap, flagging it as "an evidence-precedence question in the same family as ADR 0007, not a discovery decision," and explicitly warned against deciding it as a side effect of a different ADR. This ADR is that dedicated decision.

A real pre-existing document is very rarely complete or current. It commonly: covers only a subset of routes (a team documents the public API, not internal/admin routes); has per-operation gaps (a summary but no response schema, or vice versa); disagrees with the code on a parameter name or a path segment after a refactor no one updated the doc for; or claims a security requirement that is no longer true (or was never true) in code. A reconciliation design that only handles "the whole document matches perfectly" is not a design that will survive contact with any real repo. ADR 0007's field-level, per-operation framing already anticipates this — this ADR's job is to make that framing concrete and mechanical, and to be explicit about the one case ADR 0007's policy does not resolve on its own: what to do when the document names an operation gin-recon's analyzer never found at all.

## Decision

### Opt-in, explicit location — not implicit discovery

A reviewer names the document's path via a new config field, `analysis.existingOpenAPIDocument` (relative to `--src`, validated the same way other config-relative paths are). Empty by default: no file is read unless named. This follows the same reasoning as `analysis.followModules` (ADR 0010) — silently globbing a target repo for anything that "looks like" an OpenAPI file (`openapi.yaml`, `swagger.json`, `docs/api.yaml`, ad infinitum) is exactly the kind of implicit, un-reviewable magic ADR 0002/0003 already reject for configuration in general; a wrong guess (an unrelated YAML file, a stale generated artifact checked in by accident) silently feeding "authoritative-when-compatible" content into a report is a worse failure mode than a reviewer having to type one path.

### Parsing: reuse `libopenapi`, fail soft

The named file is parsed with the existing `libopenapi` dependency (both OpenAPI 3.0 and 3.1 documents; `libopenapi` already handles both). Three outcomes, all non-fatal to the scan itself — a malformed or missing reconciliation source degrades the report, it does not abort it, matching gin-recon's standing posture that a single problem should never silently take down the rest of an otherwise-successful scan:

- **Configured path does not exist / is unreadable** → diagnostic `openapi-spec-not-found` (severity `warning`), reconciliation skipped, scan proceeds exactly as it would with no config entry.
- **File exists but fails to parse as OpenAPI 3.x** → diagnostic `openapi-spec-invalid` (severity `warning`), same fallback.
- **Parses successfully** → reconciliation proceeds per the matching/merge rules below.

### Matching: normalize, then match by (method, path)

Gin path templates (`:param`, `*wildcard`) and OpenAPI path templates (`{param}`) are normalized to a shared comparable form before matching a document operation to a discovered `Route`. Matching is by exact (HTTP method, normalized path) pair — no fuzzy/prefix matching, since a wrong match is worse than no match (it would attribute one route's documentation to a different route).

### Merge: ADR 0007's rule, made concrete, precedence-ordered against swag (ADR 0012)

For each matched pair:

- **Never touched, unconditionally**: route existence, method, path, handler identity, middleware chain, `source`, and `authStatus`/`security`. This is ADR 0007's first sentence, restated for this specific evidence source, and reinforced by ADR 0007's own security clause: "Gin Recon never invents an OpenAPI security scheme... unknown auth is represented through `x-gin-recon`, not an OpenAPI security assertion." A pre-existing document's `security` block is exactly the kind of external assertion that clause already forbids treating as authoritative — legacy docs are disproportionately likely to be wrong or stale about auth specifically, which is the one category of error this tool exists to prevent.
- **Precedence among prose/schema sources**, highest first: (1) analyzer-resolved, structurally-typed evidence (an actually-bound Go request/response struct); (2) swag annotation evidence (ADR 0012) — colocated with the handler, more likely to be updated when the handler changes; (3) this ADR's existing-document evidence; (4) gin-recon's own generic placeholder, unchanged. A lower-precedence source only fills a field a higher-precedence source left empty — it never overwrites one that already has content. This is a direct, mechanical reading of ADR 0007's "may enrich... when code evidence is unresolved," extended one level to also defer to swag's already-established precedence over generic placeholders.
- **Structural compatibility check before accepting document content for a field**, per ADR 0007's "only when it is structurally compatible with all resolved fields and types": for a matched operation where gin-recon *does* have resolved path parameters (from Gin's own `:param` syntax) or a resolved request/response type, the document's parameter names / declared schema shape must agree before its content is used for that field. A disagreement produces diagnostic `openapi-spec-conflict` (severity `warning`) naming both the analyzer-derived and document-derived values, and the affected operation is marked `unrefined` for that specific aspect — the existing `x-gin-recon.unrefined` mechanism (used today for the "unrefined: security" case) is reused rather than inventing a parallel one. The code-derived value (or the generic placeholder, if code evidence itself was unresolved) is kept.

### Unmatched document operations: the case ADR 0007 doesn't cover on its own

An operation present in the document but never discovered by analysis (a removed route, a dynamically-registered route gin-recon's static analysis cannot resolve, or simply a wrong path/method typo in the document) is **not** synthesized into the report's `routes[]` — doing so would fabricate a "discovered" route gin-recon never actually verified in code, undermining the entire tool's evidentiary basis. Instead, it is surfaced in a new, separate report section, `existingDocumentReconciliation.orphanedOperations` (method, path, and the document's own summary if present) plus a corresponding diagnostic `openapi-spec-orphan-operation` (severity `info` — this is often completely normal, e.g. a deliberately-undocumented internal route, not a defect). Reviewers who want to know "does anything in the hand-written spec no longer exist in code" get a direct answer; reviewers who don't care can ignore the section entirely, unaffected by its presence.

### Unmatched discovered routes: no new mechanism needed

A route gin-recon discovers that the document never mentions needs no new field — this is simply the normal, current behavior of a route with no existing-document evidence attached, identical to a repo with no `analysis.existingOpenAPIDocument` configured at all.

## Consequences

A reviewer with a hand-maintained (even badly out-of-date) OpenAPI document gets it treated as a genuine, additive evidence source — filling gaps gin-recon's own static analysis and swag annotations can't, without that document ever being able to override what the tool has itself verified, especially never for auth. A conflict is a visible diagnostic + an `unrefined` marker, never a silent pick. A document that has drifted entirely (every operation orphaned, nothing matches) degrades gracefully to "as if unconfigured" plus a full orphan list a reviewer can act on — it does not corrupt or block the rest of the report.

The cost is that reconciliation is inherently best-effort against real-world document drift: a document whose paths were renamed without corresponding route changes will simply fail to match (silently, from reconciliation's perspective — though the underlying route and the underlying orphaned document operation are each still fully visible in their own report sections, a reviewer just has to notice they're related). Solving that would require fuzzy matching, which was deliberately rejected below as trading one false-positive risk for another.

## Rejected Alternatives

- **Implicit file discovery (glob for common OpenAPI filenames).** Rejected for the same reason ADR 0010 requires explicit `followModules` entries rather than auto-following every dependency: an unreviewed guess feeding into "trusted, structurally-compatible" content is a worse failure mode than requiring one config line.
- **Trust the existing document's `security`/`securitySchemes` when analysis found no configured auth evidence for a route.** Rejected outright — this is precisely the "inventing an OpenAPI security scheme" ADR 0007 already forbids, and legacy documentation is exactly the kind of source most likely to be wrong or stale about authentication specifically.
- **Fuzzy/best-effort path matching (e.g. Levenshtein distance on path segments) to handle drifted documents.** Rejected: a wrong match silently attributes one route's evidence to a different route, which is strictly worse than the current design's honest "didn't match, surfaced as orphaned" outcome. A reviewer can fix a renamed path in either the code or the document; gin-recon guessing which rename happened cannot be done safely.
- **Synthesize a `Route` entry for every orphaned document operation, marked with some "documented-only" flag.** Rejected: it would put unverified, code-absent entries in the same `routes[]` array as verified ones, forcing every consumer of the report to distinguish "real" from "claimed" routes defensively. A separate, clearly-named section is safer for every existing and future consumer of `routes[]`.
- **Treat a parse failure or missing file as a hard scan error.** Rejected: a reviewer's stale/misconfigured reconciliation path should not take down an otherwise-successful analysis of real code; this mirrors gin-recon's existing posture elsewhere (e.g. `ScanCoverage`'s partial-failure model) of degrading gracefully and reporting the problem rather than aborting.
