# ADR 0016: A `render` Command Decouples Report Formatting from Analysis

## Status

Accepted. Implemented as a fifth CLI command, `render`, registered in `internal/cli/options.go` (`CommandRender`), parsed by `internal/cli/parse.go`'s `parseRender` (its own `flag.FlagSet` with only `--report`, `--format`, `--out`, `--force`, `--config` — no `--src` or any other scan/analysis flag exists on it at all), and validated by an early, self-contained branch at the top of `internal/cli/validate.go`'s `Validate` that checks only `--report`/`--format`/`--out`, skipping every `--src`-oriented check the other commands require. Dispatched from `cmd/gin-recon/main.go`'s `run` to `runRender`, which loads `--report` with `loadReportFile` — the same function `--baseline` now also uses (`loadBaseline` is a thin wrapper over it) — validates its schema major and command with `validateRenderedReport` (using `compare.SchemaMajor`, exported for this reuse, rather than `compare.Compatible`, which would incorrectly require both sides to be audit reports), and then calls the exact same `renderReport`/`writeReport` functions `runInventory`/`runAudit` already used, so every `--format`/`--out`/companion-file rule (`api.html`, `audit.html`, `--force`) is inherited rather than reimplemented. SARIF's audit-only restriction is checked in `runRender` itself, against the loaded document's `Command` field, since `render`'s own CLI command name carries no such information the way `inventory`/`audit` do. `--config` is loaded with the same `loadConfig` inventory/audit use, but `runRender` never calls `applyConfigDefaults` — that function only fills scan/analysis `Options` fields render doesn't have.

Verified render has no code path into `internal/analyzer` or `golang.org/x/tools/go/packages`: `runRender` never imports or calls either. Tests: `internal/cli/parse_test.go` and `internal/cli/validate_test.go` (render-specific flag/validation coverage, including confirming `--src` is rejected as an unrecognized flag and a nonexistent path is never resolved) and `cmd/gin-recon/main_test.go`'s `TestRunRenderReproducesAuditOutputFromSavedReport` (byte-for-byte equality between a direct `audit --format json,openapi --out` run's `routes.json`/`openapi.json`/`api.html`/`audit.html` and `render`'s own output over that run's saved `routes.json`), `TestRunRenderSARIFAgainstInventoryReportIsRejected`, `TestRunRenderMissingReportFileFails`/`TestRunRenderMalformedReportFileFails`, and `TestRunRenderNeverTouchesASourceTree` (an isolated report file with no reachable source tree or Go module anywhere near it still renders successfully). `docs/cli-contract.md` documents the command and its Render Options section. Verified end to end against a real internal repository (`las-be-distribution`): `render --report routes.json --format json,openapi --out` reproduced the original `audit` run's `api.html`/`audit.html` and completed in a small fraction of the original scan's wall-clock time.

## Context

Every format gin-recon can produce — `routes.md`/`routes.txt`, `openapi.json`/`api.html`, `results.sarif`, and now `audit.html` (ADR 0015) — is a pure function of the same one canonical document: the `report.Report` struct that `routes.json` serializes. `internal/format/html.go`'s `HTML()` and `internal/format/audit_html.go`'s `AuditHTML()` both already take exactly one input type, `(*report.Report, *config.Config)` — neither reads `openapi.json` as a separate document; `HTML()` builds the OpenAPI model internally via `internal/format/openapi.go`'s `OpenAPI()` before rendering it. This was true before this session's own work on those two viewers, and stays true after it.

Today, the only way to regenerate any of these files — including after a purely cosmetic fix to a formatter, such as this session's own metrics/header fix to `audit_html.go` — is to rerun `inventory`/`audit` from scratch: reload the Go module with `go/packages`, redo the full static analysis, and reclassify every route, just to re-run the last, cheapest step (turning an already-computed `report.Report` back into bytes). For a large repository (`las-be-flow`: 208 packages, 440 files, 758 routes) that full reanalysis is the expensive part of the run by a wide margin; the formatting step is comparatively instant.

A sibling tool's `render` command (`express-recon`) already draws exactly this line — it "generates a static site from an existing output directory without rescanning," decoupling formatting from analysis for its own equivalent documents. gin-recon should have the equivalent capability, scoped to what its own architecture actually supports — not a port of express-recon's version, which additionally spans organizations, multiple applications, and a multi-page site with its own manifest, none of which apply here (ADR 0011 already declines multi-app/org support as out of scope for a different, unrelated reason).

## Decision

Add a fifth CLI command, `gin-recon render`, whose only input is an already-produced `routes.json` (or an equivalent, schema-valid `report.Report` JSON document — nothing else, no `openapi.json`, no directory of multiple report kinds to auto-detect) and whose only job is to re-run gin-recon's own formatting layer over it:

- **`--report <path>`** (required): a `routes.json`-shaped file. Loaded and schema-validated with the exact same validation `--baseline` already applies to a prior report (`internal/report`'s existing load/validate path) — a malformed or schema-incompatible input is a `render`-specific validation failure (exit `1`), not a silent best-effort attempt.
- **`--format`** and **`--out`**: identical semantics and identical companion-file rules to `inventory`/`audit` (`pretty|json|md|openapi|sarif`, `json`→`audit.html`, `openapi`→`api.html`, SARIF only valid when the loaded report's `command` field is `audit` — re-running SARIF formatting for an inventory-shaped report is rejected the same way requesting `--format sarif` on `inventory` already is today).
- **`--config <path>`** (optional): applies only to the parts of `config.Config` the formatting layer itself reads (`analysis.existingOpenAPIDocument`'s already-reconciled evidence stays embedded in the loaded report and is not re-resolved; `openapi.securitySchemes`/`openapi.title`-shaped output config is re-applied, since that genuinely only affects rendering, not analysis). `render` never re-runs discovery, classification, reconciliation, or auto-detection — those already happened when the input `routes.json` was produced, and `render`'s entire purpose is to not repeat that work.
- **No source tree, no `--src`, no network, no `go/packages` load of any kind.** `render` cannot execute or even read the originally-scanned repository — it only ever touches the one JSON file named by `--report` (and, if `--config` is given, that one config file). This keeps `render` inside gin-recon's existing offline-by-default posture trivially, since it has nothing to make an exception for.
- **Explicitly not built**, on the same "no gap here, wrong precedent" grounds as ADR 0011's other deferrals: multi-report/organization aggregation, a generated multi-page site with its own manifest, or any new report *content* (`render` reformats, it does not enrich, merge, or recompute anything the original run did not already decide).

## Consequences

The cheap, common case this ADR exists for — "I changed a formatter, or want a different `--format` selection, and don't want to redo a full scan" — becomes a sub-second operation reading one already-produced file, instead of requiring a full reanalysis of the original repository (which may no longer even be checked out on the machine running `render`). CI pipelines that archive `routes.json` as a build artifact gain a genuine use for that archive beyond diffing: regenerating a fresh, up-to-date-with-the-current-gin-recon-binary HTML view of a historical scan without needing to re-clone and rescan the commit it came from.

The cost is one more command surface to keep consistent with `inventory`/`audit`'s existing `--format`/`--out` rules (this ADR deliberately reuses those rules verbatim rather than inventing new ones, to keep that cost close to zero) and one clear caveat to document plainly: `render`'s output reflects whatever the *current* gin-recon binary's formatters produce, over data captured by whatever *older* binary produced the input `routes.json` — a schema-compatible but semantically stale report (e.g. reformatted after a classifier ruleset change) will render with new formatting over old evidence, and `render`'s own output should make that combination legible rather than presenting it as an equally fresh result.

## Rejected Alternatives

- **Port express-recon's full `render`, including directory-based multi-report-kind auto-detection and multi-page site generation.** Rejected: gin-recon has exactly one report kind (`report.Report`, from `routes.json`) and one repo per scan (ADR 0011); auto-detecting between report kinds that don't exist and generating a multi-page site for content that is already one page's worth of data would be speculative generality with no present need, the exact category of work ADR 0010/0011 already caution against.
- **Let `inventory`/`audit` accept `--report` as an alternative to `--src` instead of adding a new command.** Rejected: those two commands' entire identity is "run analysis," and quietly making `--src` optional in favor of a pre-computed report would blur what each invocation actually does, forcing every reader of a script or CI log to check which mode was used. A distinct command name makes the "no analysis happens here" property visible at the call site, not just in a flag's fine print.
- **Allow `render` to also accept `--src` and re-run reconciliation/auto-detection against the live repository while reusing everything else from the cached report.** Rejected: this reintroduces exactly the network/filesystem-scanning cost `render` exists to avoid, for a partial-refresh behavior with its own new set of "which parts are stale vs. fresh" questions this ADR does not need to answer. A user who wants updated analysis should rerun `audit`/`inventory`; `render` stays a pure, cheap, offline reformatting step.
